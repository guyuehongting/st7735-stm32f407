# 02 · 调试日志：9 轮，270 多组，最后发现引脚一直是对的

> 这份日志保留了每一轮的**假设 → 测试 → 结果 → 结论**，
> 包括我自己判断错的地方。失败的路也是路。

---

## 起点信息

用户能看到的只有 6 根线的丝印，其余被排针挡住：

```
已知：SCL → PB10（丝印亲眼确认）
推测：BLK → PC14 或 PC15
未知：SDA
范围：E2 E3 E4 E5 E6 C15 C13 C14 C1 C0 C3 C2 这一片
```

约束条件（由芯片决定，不是猜的）：

- PB10 只能做 SPI2_SCK → 必须用 SPI2
- SPI2 的 MOSI 只有 PC3 / PB15 → SDA 二选一
- ST7735 支持软件复位 → RES 可以不接

---

## 第 1 轮：按"常规方案"用 SPI1 扫 169 组

### 假设

1.8" ST7735 的常见接法是 SPI1（PB3=SCK / PB5=MOSI），先按这个写扫描程序：
2 个 SDA 配置 × 13 个 CS × 13 个 DC。

### 结果

**169 组全白，一组都没中。**

### 结论

回查复用表才发现致命错误：

> **PB10 在全芯片上只能做 SPI2_SCK。** 用 SPI1 的代码，时钟根本不在 PB10 上。

---

## 第 2 轮：改用 SPI2

### 改动

- 时钟改 SPI2，SCK = PB10（AF5），MOSI = PC3（AF5）
- 顺带绕开了 `HAL_SPI_MODULE_ENABLED` 没开的问题

### 结果

**还是全白。**

---

## 第 3 轮：连串口都没有输出

### 症状

用户报"什么都没打印"。

### 排查

`HAL_UART_Init()` 返回 `!= HAL_OK` → `Error_Handler()` → `__disable_irq(); while(1);`
→ 静默卡死。而且 `Backlight_On()` 排在后面，所以连背光都没亮。

### 修法（这四条后来一直沿用）

1. 串口改**纯寄存器**初始化，不依赖 HAL 模块开关
2. **第一句在 HSI 16MHz 就发**，不等时钟切到 168MHz
3. **永不调用 `Error_Handler()`** —— 给用户写测试程序，早期阶段绝不能死循环
4. 加 **LED 灯语** + 打印 `RCC->CSR`

```c
/* 灯语：3 快闪 = 进 main；5 快闪 = 168MHz OK；
         2 慢闪 = 时钟失败；1 慢闪 = 扫描结束 */
```

### 结果

```
[1] BOOT OK
[1] RCC_CSR = 0x04000000  -> PIN (引脚复位)
[2] CLOCK 168MHz OK
[3] GPIO IDR: A=0000A400 B=00004210 C=0000E000 E=00000000
```

`PIN` 而不是 `BOR` → **供电没问题**。这条信息很关键，直接排除了电源方向。

---

## 第 4 轮：想先找 BLK（失败）

### 假设

把 10 个候选脚依次拉低，屏幕变暗的那个就是背光控制脚。

### 结果

**10 个脚全拉低，屏幕一点都没变暗。**

### 结论

用户最初对引脚的描述不可靠 —— 很可能把 CS/DC 看成了 BLK。
这个方向作废，**不要再用"猜丝印"的方式推进**。

---

## 第 5 轮：SCK 锁死，扫 SDA × CS × DC（MODE 1~3）

### 设计

- SCK = PB10 固定
- SDA 只试 PC3（优先）和 PB15
- CS / DC 从 13 个候选里组合

### 结果

全白。**但出现了花屏。**

### 这是第一次真正的突破

```
纯白 = 面板一个字节都没收到
花屏 = 面板收到了字节，但命令/数据分界错了
```

ST7735 是**常白（normally white）** TN 屏，未初始化时液晶不加电、光直接透过去 = 白。
所以"能花屏"证明：供电、背光、驱动 IC、SPI 时钟、数据线**全是好的**。

---

## 第 6 轮：MODE 4，8 组 × 8 色

### 设计

给每个组合分配**不同颜色**，而不是都填绿色 ——
这样不依赖用户的反应速度，事后看颜色就能对上号。

### 结果

```
#007  CS=PC14  DC=PC15  -> 洋红
#008  CS=PC15  DC=PC14  -> 橙
（屏幕变花之后就再也没恢复）
```

### 结论

CS 一定在 PC14/PC15 里。但屏幕已经花了，后面的组全部无效。

---

## 第 7 轮：发现"花屏是粘的"

### 问题

一旦面板被点亮并显示乱码，**后面所有错误组合都改不动它**。
后续每一组看起来都是花屏，根本无法区分哪一组真的生效。

### 修法：`Clear_Panel()`

把所有候选脚一起拉低 150ms 再一起拉高。RES 一定在这 12 根线里，
所以面板一定会硬复位回白屏。

```c
static void Clear_Panel(const PinDef *sda)
{
    for (i = 0; i < POOL_N; i++)
    {
        if (sda != 0 && s_pool[i].port == sda->port && s_pool[i].pin == sda->pin)
            continue;                    /* SDA 保持 SPI 复用，不能当 GPIO 动 */
        gi.Pin = s_pool[i].pin;
        HAL_GPIO_Init(s_pool[i].port, &gi);
        HAL_GPIO_WritePin(s_pool[i].port, s_pool[i].pin, GPIO_PIN_RESET);
    }
    HAL_Delay(150);                      /* RES 低 = 复位 */
    /* ... 全部拉高，出复位 ... */
    HAL_Delay(150);
}
```

### 结果

```
#9  和 #21 花屏，其余全白
```

## 第 8 轮：找到 bug #1 —— 发像素忘了拉高 DC

### 怎么发现的

在写 MODE 6 九步诊断时逐行审代码，看到了这个：

```c
static void TFT_Cmd(uint8_t cmd)
{
    HAL_GPIO_WritePin(s_dc.port, s_dc.pin, GPIO_PIN_RESET);   /* DC = 低 */
    SPI2_Send(&cmd, 1);
}

static void TFT_WindowFull(void)
{
    ...
    TFT_Cmd(0x2C);        /* ← 最后一句，DC 停在低电平 */
}

static void TFT_FillAll(uint16_t color)
{
    ...
    TFT_WindowFull();                    /* 返回时 DC 还是低 */
    for (h = 0; h < GRAM_H; h++)
    {
        SPI2_Send(s_line, GRAM_W * 2);   /* ← 像素数据带着 DC=低 发出去 */
    }
}
```

### 为什么这是致命的

`0x2C`（RAMWR）之后的每一个字节都是**像素数据**，DC 必须是高。
而 `TFT_Cmd()` 的职责只是"拉低 DC 再发一个字节"，它**发完不会恢复**。

所以 42,768 个像素字节全部被面板当成**命令**解释。

### 影响面

**这解释了为什么 270 多组测试永远只有"白"和"花"两种结果 ——
填色这个判据从第一轮起就是坏的。**

修复：

```c
TFT_WindowFull();
DC_HIGH();          /* ★ 补上这一行 */
for (h = 0; h < GRAM_H; h++) SPI_Send(s_line, GRAM_W * 2);
```

## 第 9 轮：MODE 6 九步诊断 → 找到 bug #2

### 假设

引脚锁定 `CS=PC14 / DC=PC15`（由 #9 / #21 推出），问题在初始化序列或像素通路。

### 九步设计

```
STEP 1  Clear_Panel          屏幕回到纯白
STEP 2  初始化 + DISPON       不填色，看初始化本身有没有副作用
STEP 3  INVON  (0x21)        ★ 最关键的探针
STEP 4  INVOFF (0x20)
STEP 5  填红 / 6 绿 / 7 蓝 / 8 黑 / 9 白
```

选 `INVON` 当探针的理由：它作用于整块面板，**完全不依赖 MADCTL / COLMOD / 窗口 / 偏移**。

### 结果

```
001：STEP 2 之后都是花的
     STEP 3 花的闪了一下，STEP 4 再闪了一下，后面就不变了
002：STEP 1 白色就是白色，STEP 2 花
     STEP 3 闪了一下，后面不变，一直花
```

### 逐条解读

| 步 | 现象 | 含义 |
|---|---|---|
| 1 | 白 | 硬复位有效 |
| 2 | 花 | DISPON 生效了，GRAM 是上电随机值（正常） |
| 3 | 闪一下 | **命令到了** ✓ |
| 4 | 再闪一下 | **命令到了** ✓ |
| 5~9 | 一点不变 | **数据一个都没进去** ✗ |

**命令通路全通，数据通路全断。**

### 电路上只有一种解释

```
我们以为：PC14 = CS（恒定拉低），PC15 = DC（翻转）
实际情况：PC14 = DC（被恒定为低 → 永远命令模式 → 命令全进 ✓）
          PC15 = CS（在跳）
             · 发命令时 PC15 恰好被拉低 → 片选有效 → 命令进得去 ✓
             · 发数据时 PC15 被拉高   → 片选失效 → 数据全丢 ✗
```

顺便解释了为什么填色"一点变化都没有"：
`0x2A / 0x2B` 的参数也丢了 → 窗口停在 `(0,0)-(0,0)` 这 1 个像素 → 整屏看起来完全没动。

---

## 第 10 轮：MODE 8，一次跑两套顺序 → 通了

### 设计

不再推理，一次烧录把两种顺序都跑一遍：

```
PHASE A   CS=PC15  DC=PC14   -> 红 绿 蓝 白（各 2 秒）
PHASE B   CS=PC14  DC=PC15   -> 红 绿 蓝 白（各 2 秒）
```

### 结果

**PHASE A 出纯色。**

### 定案

```
SCK = PB10
SDA = PC3
CS  = PC15
DC  = PC14
RES = 不接（SWRESET）
```

---

## 回头再看 MODE 7 的 #009 / #021

MODE 7（INVON 扫描）里两组都能让屏幕变化，当时以为分不出对错。

| 组合 | 真 DC | 真 CS | INVON 能不能进 |
|---|---|---|---|
| #009 `CS=PC14 / DC=PC15` | PC14 恒低 → 永远命令模式 | PC15 在跳 → 命令期恰好低 | **能** ✓ |
| #021 `CS=PC15 / DC=PC14` | PC14 在跳 → 正常 | PC15 恒低 → 一直选中 | **能** ✓ |

**只有 #021 是两路全对的**，#009 只是靠"命令期 CS 恰好低"蒙进去的。

这就是为什么当时选错了方向：**无参数命令能证明"命令通路"，
但区分不了 CS/DC 顺序。**
