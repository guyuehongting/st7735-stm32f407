# ST7735S 1.8" TFT on STM32F407 —— 从"全白"到点亮，一次完整的踩坑复盘

> 一块 1.8 寸 128×160 SPI TFT（ST7735S），接在 STM32F407VET6 上，屏幕只给白屏和花屏。
> 前后扫了 **270 多组引脚组合**，最后发现**引脚一直是对的，错的是两行代码**。
>
> 这个仓库把整个过程、9 版测试程序、以及最终可用的驱动都留下来了，
> 希望下一个遇到"白屏/花屏"的人能少走几天弯路。

## 一句话结论

**如果 ST7735 只出白屏或花屏，先别急着扫引脚 —— 先确认这两件事：**

1. **CS 和 DC 有没有接反**（命令能进、数据全丢，就是反了）
2. **发像素之前有没有把 DC 拉高**（`0x2C` 之后每一个字节都是数据）

这两条错了，扫一万组引脚也不会有结果。

## 最终接线（已验证）

| 模块丝印 | 也可能写作 | 接到 | 说明 |
|---|---|---|---|
| VCC | VDD / 3V3 | **3.3V** | |
| GND | GND | **GND** | |
| SCL | SCK / CLK | **PB10** | SPI2_SCK（AF5） |
| SDA | MOSI / DIN | **PC3** | SPI2_MOSI（AF5） |
| CS | CE / SS | **PC15** | 片选，低有效，程序里常低 |
| DC | A0 / RS | **PC14** | 命令=低 / 数据=高 |
| RES | RST | **不接**（但必须拉高） | 用软件复位；**悬空会被噪声复位，驱动里已把所有备用脚拉高钉住** |
| BLK | LED / BL | **3.3V** | 想调亮度改接 PB8 做 PWM |

> **RES 不接 ≠ 不用管。** 悬空时跑几秒就会被噪声拉低，面板自己复位回白屏 ——
> 症状就是"闪几个颜色就变纯白，之后再也不动"。
> `driver/main.c` 里的 `TFT_ParkPinsHigh()` 把所有"没用到但可能是 RES"的脚
> 用**输入上拉**钉在高电平，这是让屏幕能稳定跑下去的关键一步。
> **实测：加上这一步之后，屏幕一路正常计数到 300+。** 详见 [docs/03-pitfalls.md](docs/03-pitfalls.md)。

> **为什么是 SPI2 而不是 SPI1**：因为 SCL 物理上接在 PB10，而 PB10 在全芯片上**只能**做 SPI2_SCK。
> SPI2 的 MOSI 只有两个选择：**PC3** 或 PB15。

## 现象速查表

遇到问题先查这张表，能省掉 90% 的时间。

| 现象 | 最可能的原因 | 怎么确认 |
|---|---|---|
| **纯白，完全没反应** | SCK / SDA / CS 至少错一个 | 面板一个字节都没收到 |
| **花屏** | 收到字节了，但**命令/数据分界错了** → DC 有问题 | 见下方"命令通/数据断" |
| **命令生效但填色不变** | ① CS/DC 反了 ② 发像素前 DC 没拉高 | 见[两个根因](#两个真正的根因) |
| **闪几个颜色后变纯白，再也不动** | **RES 悬空，面板自己复位** | 串口还在打印 = MCU 活着 = 就是这个 |
| 白屏但串口一直正常打印 | 同上（MCU 跑得好好的，是面板被复位） | `TFT_ParkPinsHigh()` 输入上拉钉住 RES |
| 白屏但串口正常打印 | 面板被复位 / 供电跌落 | 拉高所有备用脚，或把 RES 接出来 |
| 填色有变化但整体花 | 窗口参数丢了 → 窗口退化成 1 像素 | 打印 CASET/RASET 参数 |
| 纯色但红蓝互换 | BGR 顺序 | `USE_BGR` 改 1 |
| 画面上下/左右颠倒 | MADCTL | `MADCTL_VAL` 换一个 |
| 边缘 1~2 像素杂色 | 132×162 vs 128×160 的偏移 | `X_OFF=2` / `Y_OFF=1` |
| 大面积正常、细线错位 | SPI 太快 | `SPI_BR` 降一档 |

### 白屏 vs 花屏，是两种完全不同的故障

这是整个调试里最有用的一个判据：

```
纯白  = 面板一个字节都没收到   → SCK / SDA / CS 至少错一个
花屏  = 面板收到了字节，但内容乱 → SCK/SDA/CS 全对，只有 DC 错
```

ST7735 是**常白（normally white）** TN 屏：液晶不加电时是透光的，所以未初始化就是白的。
能出花屏，说明**供电、背光、驱动 IC、SPI 时钟、数据线全部是好的**。

## 完整调试历程（9 轮）

### 起点：只能看到 6 根线的丝印

用户提供的已知信息：

- `SCL` → **PB10**（丝印亲眼确认）
- `BLK` → PC14 或 PC15（不确定）
- `SDA` → 不知道
- 其余引脚被排针挡住，只知道大致在这一片：`E2 E3 E4 E5 E6 C15 C13 C14 C1 C0 C3 C2`

### 第 1 轮：用 SPI1 扫 169 组 → 全白

按"PB3=SCK / PB5=MOSI"的常规方案写了扫描程序，2 个 SDA × 13 个 CS × 13 个 DC。

**结果：169 组全白，一组都没中。**

### 第 2 轮：发现总线搞错了

回查 STM32F407 的复用表才发现：

> **PB10 在全芯片上只能做 SPI2_SCK。** 用 SPI1 的代码去驱动 PB10，时钟根本不在 PB10 上。

改为纯寄存器 SPI2（顺带绕开了 `HAL_SPI_MODULE_ENABLED` 没开导致的 `SPI_HandleTypeDef is undefined`）。

**结果：还是全白。**

### 第 3 轮：连串口都没输出

`HAL_UART_Init()` 返回失败 → `Error_Handler()` → `__disable_irq(); while(1);` → 静默卡死，
连背光都没来得及点亮。

修法：串口改纯寄存器、第一句在 HSI 16MHz 就发、**永不调用 Error_Handler**、加 LED 灯语、打印 `RCC->CSR`。

```c
/* 3 快闪 = 进 main；5 快闪 = 168MHz OK；2 慢闪 = 时钟失败 */
```

`RCC_CSR = 0x04000000 (PIN)` → 没有 BOR → **供电没问题**，排除电源方向。

### 第 4 轮：两阶段扫描，想先找 BLK

思路：把 10 个候选脚依次拉低，屏幕变暗的那个就是 BLK。

**结果：10 个脚全拉低，屏幕一点没变暗。**

结论：**用户最初对引脚的描述不可靠**（很可能把 CS/DC 看成了 BLK）。这个方向作废。

### 第 5 轮：SCK 固定，扫 SDA × CS × DC（MODE 1~3）

SCK 锁死 PB10，扫 2 个 SDA × 13 个 CS × 12 个 DC。

**结果：全白。** 但发现一个奇怪现象 —— 某些组合会出现**花屏**。

这是第一次突破：**花屏说明字节真的到面板了。**

### 第 6 轮：MODE 4，8 组关键组合 × 8 种颜色

给每个组合分配不同颜色，避免"都是绿色"分不清。

**结果：`#007 CS=PC14 DC=PC15 → 洋红`、`#008 CS=PC15 DC=PC14 → 橙`，而且屏幕变花之后再也没恢复。**

### 第 7 轮：发现"花屏是粘的"

一旦面板被点亮并显示乱码，**后面所有错误组合都改不动它**。
后续每一组看起来都是花屏，根本无法区分。

修法：每组开始前 `Clear_Panel()` —— 把所有候选脚一起拉低 150ms 再一起拉高。
RES 一定在这 12 根线里，所以面板一定会硬复位回白屏。

```c
static void Clear_Panel(const PinDef *sda)
{
    /* 全部拉低 150ms -> RES 被拉低 -> 面板复位 -> 白屏 */
    for (i = 0; i < POOL_N; i++) { ... GPIO_PIN_RESET; }
    HAL_Delay(150);
    /* 全部拉高 -> 出复位 */
    for (i = 0; i < POOL_N; i++) { ... GPIO_PIN_SET; }
    HAL_Delay(150);
}
```

**结果：`#9` 和 `#21` 花屏，其余全白。**

### 第 8 轮：找到 bug #1 —— 发像素忘了拉高 DC

在准备 MODE 6 九步诊断时翻代码，发现：

```c
static void TFT_WindowFull(void)
{
    ...
    TFT_Cmd(0x2C);        /* ← 最后一句，把 DC 拉成了低 */
}

static void TFT_FillAll(uint16_t color)
{
    ...
    TFT_WindowFull();                    /* 出来时 DC 还是低 */
    for (h = 0; h < GRAM_H; h++)
    {
        SPI2_Send(s_line, GRAM_W * 2);   /* ← 像素数据带着 DC=低 发出去 */
    }
}
```

`TFT_Cmd()` 的职责是"拉低 DC 再发一个字节"，它**发完不会恢复 DC**。
所以 `0x2C` 之后的四万多个像素字节全部被面板当成**命令**解释。

**这解释了为什么 270 多组测试永远只有"白"和"花"两种结果 —— 填色这个判据从一开始就是坏的。**

### 第 9 轮：MODE 6 九步诊断 → 找到 bug #2

修完 DC 后跑九步（当时假设 CS=PC14 / DC=PC15）：

```
STEP 1  Clear_Panel    -> 白 ✓
STEP 2  初始化 + DISPON -> 花（GRAM 是上电随机值，正常）
STEP 3  INVON          -> 闪一下 ✓   命令到了
STEP 4  INVOFF         -> 再闪一下 ✓ 命令到了
STEP 5~9 填红绿蓝黑白  -> 一点不变 ✗ 数据一个都没进
```

**命令通路全通，数据通路全断。** 这在电路上只有一种解释：

```
我们以为：PC14 = CS（恒低），PC15 = DC（翻转）
实际情况：PC14 = DC（恒低 → 永远命令模式 → 命令全进 ✓）
          PC15 = CS（在跳 → 命令期恰好低 → 命令进；数据期拉高 → 数据全丢 ✗）
```

### 第 10 轮：MODE 8 一次跑两套顺序 → 通了

与其继续推理，不如一次烧录把两种顺序都跑一遍：

```
PHASE A   CS=PC15  DC=PC14   -> 红 绿 蓝 白
PHASE B   CS=PC14  DC=PC15   -> 红 绿 蓝 白
```

**结果：PHASE A 出纯色。引脚定案：`CS = PC15`，`DC = PC14`。**

## 两个真正的根因

### 根因 1：CS / DC 接反

**症状**：命令全通，数据全断。

- `SWRESET`、`SLPOUT`、`DISPON`、`INVON`、`INVOFF` 全部生效（屏幕会闪）
- 但所有带参数的命令（`0x2A/0x2B` 窗口、`0x36` 方向、`0x3A` 色深）和所有像素数据全部丢失
- 填色"一点变化都没有"，因为窗口退化成 1 个像素

**为什么两种接法都会"闪"**：`INVON` 是**纯命令、没有参数**，两种接法都能把它送进去。

```
#009 CS=PC14 / DC=PC15：PC14 恒低 → 永远命令模式；PC15 在跳 → 命令期恰好低 → 命令进 ✓
#021 CS=PC15 / DC=PC14：PC14 在跳 → 正常；PC15 恒低 → 一直选中 → 命令进 ✓
```

**只有 #021 是两路全对的**，#009 只是靠"命令期 CS 恰好低"蒙进去的。

### 根因 2：发像素前没把 DC 拉高

```c
TFT_Cmd(0x2C);          /* 这个函数把 DC 拉低，而且不恢复 */
DC_HIGH();              /* ★ 漏了这一行，后面几万个像素全被当成命令 */
for (h = 0; h < GRAM_H; h++) SPI_Send(s_line, GRAM_W * 2);
```

`0x2C`（RAMWR）之后的每一个字节都是**像素数据**，DC 必须是高。

## 方法论总结

这五条是这次最值钱的收获。

### 1. 判据坏了，扫一千组也没用

多轮扫描永远只有"白"和"花"两种结果时，**第一件事是审判据代码，不是扩大扫描范围**。
这次 169 + 48 + 37 + 24 组全部白扫，因为填色这个判据本身就是坏的。

### 2. 定位探针要选"依赖最少"的那个

| 判据 | 依赖什么 |
|---|---|
| 屏幕变绿 | 命令对 + 参数对 + COLMOD 对 + 窗口对 + MADCTL 对 + 偏移对 |
| **屏幕变黑（`0x21` INVON）** | **只要命令能到面板** |

`0x21` 是整屏动作，不经过显存、不经过窗口、不看 MADCTL，是最干净的探针。

### 3. 但无参数命令区分不了 CS/DC 顺序

两种接法都能把 `INVON` 送进去。**要区分顺序，必须用"带参数的命令"或"写像素"这类依赖 DC=高 的动作。**

### 4. 盲测必须保证每组初始状态可复位

"花屏是粘的"：一旦面板被点亮并显示乱码，后面所有错误组合都改不动它。
每组开始前把所有候选脚拉低 150ms 硬复位，判据才干净。

### 5. 别用别的板子的引脚分配去裁剪用户的候选集合

第一轮我把用户列的 12 个脚砍成 4 个（理由："PE2~PE5 是按键"），直接导致 48 组全白。
**用户自定义板子的引脚分配只能实测，不能假设。**
